## Schema and access

- `member_profiles`: private account fields, username uniqueness (case insensitive), display-name constraints, avatar choice/path constraints. SELECT/INSERT/UPDATE policies restrict records to `id = auth.uid()`; anonymous access is not granted. The initial migration grants authenticated users table-level SELECT/INSERT/UPDATE, so owners can also set their timestamps; this matches the live history.

- No public-schema triggers were present.
- Public strain rows/reviews expose creator/user UUIDs under the historical SELECT grants. Public review photos also contain owner UUIDs in object paths. They do not expose profile email addresses. No privacy model changes were made.

## Why the declined SQL needed review

It contained INSERT/UPDATE/DELETE inside BEGIN ... ROLLBACK. Review IDs `r` and `d` came from newly inserted test rows, so its DELETE statements targeted test reviews. It also temporarily updated avatar fields on one existing member profile, inside an exception subtransaction. It did not use DROP, TRUNCATE, or unrestricted UPDATE.

Postgres rolls back transactional row changes when the complete transaction is executed and ends in ROLLBACK (or aborts). That is conditional on execution preserving a single transaction and not committing fragments independently. A committed fragment updating the profile could permanently change existing avatar data. Sequence advances are not generally rolled back, though this batch did not insert a new identity-backed strain. The tool returned "SQL execution was declined"; no tests in that batch ran.

Future live writes require the user's explicit approval under their latest instruction.
